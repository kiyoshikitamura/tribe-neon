# 第10工程 UI — 未確定Room出撃の再読込復帰

状態: IMPLEMENTED。親レビュー・機械検証はRAID-P/C-10の記録を参照。実DB・実機・本番適用は未検証。

## 保存と正本

`raidRoomBattlePending.ts` はユーザーID別localStorageへversion、userId、Room ID、request UUID、順序固定のcharacter IDs、tacticのみ保存する。Snapshot、Damage、勝敗、RP、報酬は保存正本にしない。開始RPCより先に保存とreadbackを完了し、保存失敗なら開始しない。既存の別要求を上書きしない。破損した記録を自動削除して新要求へ置換しない。

再読込時は`get_raid_room_battle_start_receipt_v1`で本人の開始台帳を読む。応答ありならサーバーSnapshotと同Replayを使用する。nullは未送信の証明と扱わず、保存した同request・同payloadだけで開始RPCを再送する。現在の編成・総合力・期限・運用flagを利用して保存済み開始応答を置換しない。現在Roomの表示情報は参照RPCで取得するが、新規出撃資格の判定として使用しない。

開始応答内のremaining_raid_pointsは開始時点の履歴値のため、復帰時にはこの履歴値で現在のRP/初回無料表示を上書きしない。確定成功後に`get_current_raid_attempt_state`で現在値を取得する。参照失敗時は既存表示を保持し、戦闘再開始はしない。新規開始の場合のみ従来の更新を継続する。

## 製品接続

`useBattle.resumePendingRaidRoomBattle`をGameContextの通常セッション復帰より優先する。既存の手動ResumeとRoom準備入口も同入口を使用する。処理中は同promiseに合流し、未確定記録がある場合はエラー時も旧セッションへ進まない。Room表示中の参照を保持し、pending削除後の別復帰による上書きを防ぐ。

サーバー確定結果と表示stateを復元し、同ReplayのACTIVE互換セッションを参照する。既存があれば再利用し、なければ保存する。互換セッション保存成功と表示到達後にのみpendingを削除する。互換保存/削除失敗なら記録は残り、次回も同Replayを再確認する。これは複数タブ同時insertの一意性をDBで保証する変更ではない。

アカウント切替では旧ユーザーのrefと表示を解放し、保存は各ユーザー領域に残す。準備・開始・復帰・確定の通信前後でユーザーを照合し、旧アカウントの遅い応答を現在の表示へ反映しない。通常の未送信取消は許可し、結果不明の開始送信後は別要求の生成を防ぐ。通常の確定DBエラー後の取消は当該保存記録を削除する。

## 限界・停止条件

- localStorage消失・別端末・記録破損からのサーバー未確定要求の全件探索は未実装。破損・アクセス不能は自動破棄せず停止する。
- 復帰時にreceiptがnullで、同request開始が期限/運用停止等で拒否された場合、保存を勝手に破棄しない。この状態では停止・再確認となり、サーバー確定を伴う取消導線は未実装。
- 複数タブ/端末で異なる新requestを同時作成する制御は本工程に含まない。同request再送はDB台帳の冪等性を利用する。
- 互換セッションは再開表示用であり、戦闘確定・HP・消費はサーバーReplay/Room台帳が正本。
- 作成/開始の運用設定と製品Room露出の既定falseを維持する。救援・報酬・ランキング切替・実DB・実機は残件。
